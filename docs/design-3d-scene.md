# 3D 摆姿场景的技术选型

日期:2026-09-24。范围:只讨论 3D 摆姿场景本身,不含模型生图。

## 1. 目标与硬约束

要做的事:一个简化人体模型(宜家小人那种)、骨架绑好、可拖拽关节移动与旋转、摆出各种姿势、
正反向运动学、并限制在正常人体可能的骨骼旋转范围内。

硬约束来自 Haminn happ 本身(见 `AGENTS.md`):

- 纯原生 HTML / CSS / JavaScript,没有构建步骤,不使用打包器。
- 不联网加载模块,不引 CDN。第三方库必须原样放入 `vendor/`。
- 兼容 Android 10 与旧厂商 WebView,实测等价 Chrome 83。
- MIT 许可,因此不能混入 GPL 代码。

## 2. 先澄清一个术语

这里说的"正反向动力学",在摆姿场景里实际指的是**运动学 kinematic**:

- **FK 正运动学**:给关节角度,算出手脚末端在哪。我们只做"把角度写进层级"就完事了。
- **IK 反运动学**:给手脚末端目标位置,反解出关节角度。这是"拖手拖脚"手感的来源。
- **动力学 dynamics**:力、质量、惯性、重力、碰撞。MagicPoser 宣传的"物理引擎自动生成自然姿势"
  属于这一层。

结论:摆姿这个场景 95% 的体验价值在 FK + IK + 关节限制。动力学是加分项,第一版不做,
最多后面加一个"重心投影提示"这种很轻的辅助。把动力学当成必做项会把工作量放大一个量级,
而收益主要在极端姿势与摔倒动作,不是我们要的东西。

## 3. 开源项目调研(许可已逐个核实)

| 项目 | 许可 | 算法 | 关节限制 | 对我们可用性 |
|---|---|---|---|---|
| three.js 自带 `CCDIKSolver` | MIT | CCD | r147 经典脚本版只有单轴 `limitation`;r160 起重写为 `rotationMin/rotationMax` 欧拉盒夹取 | 需要 `mesh.skeleton.bones`,即要求 SkinnedMesh |
| `lo-th/Fullik` | MIT(471★) | FABRIK + CCD | 支持逐关节约束 | 有经典脚本,但 API 重、按老版 three 写 |
| `jsantell/THREE.IK` | MIT(586★) | FABRIK | 提供 `constrain()` 钩子,范围自己写 | 需要自己转成经典脚本 |
| `upf-gti/IK-threejs` | MIT(23★) | CCD + FABRIK | 有 ball-socket / hinge 与角度范围,最贴需求 | 只有 ESM 源码,零构建步骤下不能直接用 |
| `boytchev/mannequin.js` | **GPL-3.0**(430★) | 只有 FK,没有 IK | 没有硬性角度限制,只提示"负值不自然" | **代码不能进 MIT 项目** |
| `Callum-OP/3D-Character-Animator` | 无许可声明 | 变换 gizmo,非 IK | 无 | 只能看思路,不能复用 |

三个关键事实是我读源码确认的,不是猜的:

1. three.js r147 的 `examples/js/animation/CCDIKSolver.js` 确实存在,导出 `THREE.CCDIKSolver`
   与 `THREE.CCDIKHelper`,是经典脚本,能用。但它内部直接 `this.mesh.skeleton.bones`,
   **必须要一个 SkinnedMesh**,我们这种刚性分体小人用不了(除非造假对象绕开,见 5.3)。
2. 同一份 r147 文件里**没有** `rotationMin` / `rotationMax`,只有单轴 `limitation`。
3. r160 才加了 `rotationMin` / `rotationMax`,实现方式是:每一轮 CCD 迭代之后,
   把该 link 的欧拉角按分量夹进给定范围。

第 3 条很重要,它说明连 three.js 官方对"关节限制"的处理方式就是**迭代后夹取**,
不是把约束做进求解过程。这给了我们自己写求解器的正当性。

## 4. MagicPoser 与 SetPose 的技术对照

MagicPoser(`webapp.magicposer.com`)对外说明的能力:符合人体解剖与运动学的求解器、
手部与脚部的成熟 IK、拖拽控制点摆姿、物理引擎自动生成自然姿势、逐指控制、姿态库与镜像。

它的交互范式是"每个关节一个控制点,拖就是了"。这对我们没有直接可抄的代码(GPL 与闭源),
但指出了三件事必须做到:IK + 解剖限制 + 语义化的关节控制。

更值得抄的是 **SetPose**(同样 three.js 系,构建在 mannequin.js 之上)的做法,它更接近"简单够用":

- 每个肢体只有三个语义通道:**Bend(屈伸)/ Tilt(侧摆)/ Rotate(自转)**,不是自由欧拉角。
- 一个 **Biological constraints 开关**:打开按关节活动范围限制,关闭则放开到 ±180,允许夸张造型。
- 道具可以 attach 到关节上,换姿势时跟着走。

第四个参考是 mannequin.js 自己的关节命名:手臂与腿用 `raise / straddle / turn`,
头用 `nod / turn / tilt`,躯干用 `bend / turn / tilt`。这说明"按解剖语义命名三个通道"
不是权宜之计,而是一个成熟库的选择。

## 5. 建议方案

### 5.1 模型:人物模型离线切成的"骨架 + 刚性件"(2026-09-25 改定)

**现状**:人物是**外部模型**(宜家人偶 `manniquin.glb`,由 `tools/import-model.py` 离线转换),
不再是程序化生成的几何。做法:每个关节挂一件刚体网格,顶点写在**关节局部坐标系**里
(原点 = 关节,骨骼方向 = 局部 +Y),视口只按 FK 给出的矩阵摆放。

- 不需要蒙皮、不需要骨骼权重、不需要 GLTFLoader。运行时零依赖。
- 骨架的 `offset` / `rest` / `length` / `radius` **全部来自模型**(`app/assets/models/*.js`),
  `rig.js` 的关节表里只留"怎么抓、能转多少"这类与几何无关的字段。
- 只有一样东西的尺寸是视口定的:**关节把手球**(`NODE_RADIUS`)。
  模型给的 `radius` 是**零件包围球半径**(小腿 0.216、髋 0.24),拿来当球半径会得到
  比脑袋还大的球,整条腿都被盖住、点空地就再也点不中(真机反馈过)。
- 例外是**肩**(2026-09-25 修):宜家模型的 `shoulder.L` / `shoulder.R` 件本身就是
  一颗 42 顶点的球,而我们画的球 R 0.0531 比它(R 0.0550)还小 —— 在关节原点再画一颗,
  就会在肩上叠出**两颗互相穿插的球**(用户反馈过)。所以肩直接**用模型自带的那颗球当把手**,
  视口不另画。
- 由此定下一条不变量:**把手球的球心必须落在关节原点上**。视口与命中的锚点取的就是
  关节原点,球心一偏、锚点跟着偏,表现成"看着点在球上却掉进空地"。
  这里曾经有个补偿字段 `nodeOffset`:模型那颗肩球的球心偏出关节原点 **47.4mm**
  (关节局部坐标,左右基本镜像),视口画的球按它摆位、命中锚点也按它挪。
  但屏幕容差(`NODE_GRAB_PX`)只有 33px,而 47.4mm 在设备上约 **23px** ⇒
  球心那一侧只剩 10px 余量,**球的外半边点不到** —— 之所以一直没被用户抓到,
  就是这个 23px < 33px 把问题盖住了。
  **骨架按人体测量学校正后球心已归零**(实测球块质心 0.0mm),补偿与字段一起删掉;
  `tests/ik.test.mjs` 现在不查字段,而是**直接量球块质心**守着这条。
- 量过的对照:12 颗模型关节球里,球心与转动原点偏离的**只有肩(47.8mm)**,
  髋 6.2mm、肘 4.5mm、膝 4.2mm、腕 3.6mm 都在网格精度内 —— 所以只有肩需要动几何。

曾经的做法(2026-09-24,已废弃):照宜家木人程序化画锥形圆柱 + 球关节,
`taper` / `shape` / `boneOffset` 三个字段都是那个时候的产物,现已从关节表删除 ——
模型自带的网格已经决定了粗细与轮廓,再留一套"程序化画法"的参数就是两处各说各话。
`head` 是椭球、脚掌靠 `boneOffset` 下沉这些细节随之作废。

### 5.1.1 拖动语义(哪一块抓起来算什么)

`grab` 管**关节把手球**,`meshGrab` 管**零件网格**,两者是两件不同的事
(曾经合并成一个函数,真机上表现为"小臂、小腿选不中"):

| 字段 | 作用 |
| --- | --- |
| `node` / `nodeScale` | 在该关节**原点**画一颗可抓的球(肩、肘、膝、踝、腕);躯干不画。尺寸 = `NODE_RADIUS × nodeScale` |
| `nodeFrom: "model"` | 这个关节的把手球**由模型自带的那颗**承担,视口不另画(目前只有肩)。它的球心必须落在关节原点上 —— 命中锚点就是原点,`tests/ik.test.mjs` 直接量质心守着 |
| `grab` | 拖这颗球算什么:`node` 移动(走 IK)/ `bone` 旋转。不写就按"上游有没有可转的关节"推 |
| `meshGrab` | 拖这整块零件网格算什么。目前只有手与脚写它 —— 腕球、踝球负责把肢体拉过去,而手掌、脚掌自己抓住要能转角度 |
| `limit {x:[min,max]}` | 该关节的可转范围,记的是**相对静止姿态的增量**(模型的 rest 可能是任意值)。目前只有手与脚声明 |

手与脚的范围按人体活动度:手腕掌屈 80 / 背伸 70、桡尺偏 ±25、几乎不能自转;
脚踝勾脚背 25 / 绷脚背 50、内外翻与内外摆各 ±20。

### 5.2 关节模型:三个通道 + 解剖范围表(**2026-09-25 落地**)

每个关节三个通道 `x / y / z`,窗口写在 `app/core/rig.js` 的关节表里。
窗口记的是**相对静止姿态的增量**,不是绝对角度 —— `rest` 来自人物模型,可能是任意值
(宜家脚踝的 rest x 是 65.4 度、大腿的 rest z 是 -178.7 度),写绝对角度会一上来就被夹飞。
没写窗口的关节沿用全局 ±180;**现在一个都没落下**(包括纯变换节点 broot 的三个零宽窗口)。

#### 三个通道到底对应哪个动作(**实测,不是"按常理定的"**)

骨骼沿各自局部 +Y 生长,所以 **y 恒等于"绕骨轴自转"**;另两轴按"绕它转 +10 度时,
骨末端往哪挪"逐关节量出来(探针:`channels.js`,结果见下):

| 通道 | 躯干与头(hips/spine/chest/neck/head) | 四肢(肩/臂/腿/脚) |
| --- | --- | --- |
| `x` | +x → 末端朝 +Z(**前**)⇒ +x = 前屈 / 低头 | +x → 末端朝 +Z ⇒ +x = 前摆 / 屈 |
| `z` | +z → 末端朝 **-X**(角色的右)⇒ +z = 向右侧倾 | +z → 末端朝 +X(角色的**左**)⇒ +z = 朝左走 |
| `y` | +y = 面朝方向转向 +X(向左转) | 绕骨轴拧(外展/内收的镜像规律见下) |

`z` 两边方向相反不是笔误:躯干的骨朝上、四肢的骨朝下,绕同一根世界轴转,末端自然朝相反方向去。

#### 朝向:三面四方是量出来的,不要凭"看起来像"

一次实测(探针 `facing.js` / `footshape.js` / `butt.js`,2026-09-25):
**角色面朝 +Z、角色自身的左侧 = +X、上 = +Y**。三条互相独立的证据:

1. **脚尖方向**:`foot.L` 相对踝关节朝 +Z 伸 0.1506 m、朝 -Z 只伸 0.0623 m。
   人的踝关节离脚跟约 29% 脚长,0.062/(0.151+0.062)= 29% —— 吻合 ⇒ +Z 那头是脚尖。
2. **脚掌厚度剖面**(和上一条无关):沿脚长由 -Z 到 +Z 的厚度是
   `0.058 → 0.066 → 0.067 → 0.059 → 0.050 → 0.062 → 0.052 → 0.041 → 0.028 → 0.016` 米。
   最薄的那端(0.016 m)是脚趾,最厚那端是带踝隆起的脚跟 ⇒ **脚尖朝 +Z**。
3. **脚骨朝向**:`foot` 骨从踝出发指向 `(-0.10, -0.41, 0.91)`,即向前下方约 24 度 ——
   正是"踝→前脚掌"的方向。

左右由人物模型自己的骨骼命名给出(`Arm.L_011` / `Thigh.L_01`,GLB 源里的 L/R 是**角色自身**
的左右),与"面朝 +Z 时左侧在 +X"一致:`shoulder.L` 的横向偏移是 **+0.1427 m**、`thigh.L` 是 **+0.082 m**。

> 曾用"大脚趾在内侧"再验一次,结论是**没有结论**:这具人偶的脚是左右对称的纺锤形,
> 趾端相对踝的横向偏移只有 0.2~0.8 mm(纯噪声)。这条判据在这个模型上不可用,别拿它当证据。

#### 由此得出的一条硬规则:左右只在 y 与 z 上互为相反数

`x` 通道左右**完全一致**,`y` 与 `z` 取反(上下界跟着交换)—— 这正是 `mirror()` 的定义。
所以成对关节的窗口一律由 `mirroredLimit(左侧)` 生成,不手抄:抄一遍就是把
"右腿外展"写成"内收",真机表现是"一条腿能往左跨、另一条不能"。

反关节的唯一入口是**单侧窗口**,所以膝与肘必须写成单侧:

| 关节 | x(屈伸) | y(绕骨轴) | z(侧摆) |
| --- | --- | --- | --- |
| hips 骨盆 | -25..25 | **-180..180**(全身转向盘) | -20..20 |
| spine 腰 | -35..15 | -15..15 | -25..25 |
| chest 胸 | -40..25 | -40..40 | -30..30 |
| neck 颈 | -35..40 | -50..50 | -30..30 |
| head 头 | -20..25 | -30..30 | -15..15 |
| shoulder.L/R | -20..60 | ±30 | -10..60(右侧镜像) |
| upperArm.L/R | -45..125 | ±70 | -35..125(右侧镜像) |
| forearm.L/R 肘 | **0..145**(下界 0 = 不许反张) | ±85 | ±10 |
| hand.L/R 腕 | -70..80 | ±25 | ±25 |
| thigh.L/R 髋 | -25..120 | ±45 | -30..45(右侧镜像) |
| shin.L/R 膝 | **-150..0**(上界 0 = 不许反张) | ±20 | ±6 |
| foot.L/R 踝 | -50..25 | ±20 | ±20 |

窗口加起来要落在整条链的实数里,例:躯干三节 = 前屈 100 / 后伸 65 / 旋转 55 / 侧屈 75;
颈 + 头 = 前屈 55 / 后伸 65 / 旋转 80 / 侧屈 45;肩 + 上臂 = 前屈 185 / 后伸 65 / 外展 185。

**测试守着**:`tests/rig.test.mjs` 有四条契约(每个关节都写满三通道 / 成对关节窗口必须镜像 /
膝肘单向 / 髋的 y 给满) + 一条几何验证(把膝与肘在自己的窗口里扫一遍,
踝**永远不许跑到膝前方**、腕**永远不许跑到肘后方**)。
**预设也跟着改了**:旧 `sit` 把大腿写成 -88(髋后伸)、小腿写成 +85(膝反张),
`walk` 的右膝写 +35,`wave` 用肩的 x 后甩 130 度"举手" —— 全是反关节,限制上线后会被夹成废pose,
已按实测的通道语义重写(举手上臂伸直**改走 z 外展** 60+105,坐下**髋 +86 / 膝 -86**)。

### 5.3 IK:解析式两骨 + 自写 CCD,约 200 行,不引依赖

**落地情况(2026-09-25)**:两层都有了。`app/core/ik.js` 的 `solve()` 按链长路由:

| 链 | 走哪条路 | 例 |
| --- | --- | --- |
| 恰好两节、且两段都有长度 | **解析式闭式解** `solveTwoBone` | 拖脚踝(大腿 + 小腿) |
| 退化的两骨链(第一段长度为 0) | 退回 CCD | 拖肘部(肩与上臂**同原点**,上臂相对肩的位移是 0) |
| 单关节链 | CCD | 拖膝(只有大腿可转,膝盖只能落在绕髋的球面上) |
| 三节及以上 | CCD | 拖手、拖头 |

为什么**必须**有第一层(踩出来的,不是"更优雅所以做"):

> CCD 的每一步都是"把末端指向目标"。抬脚向前上方时,膝盖唯一合法的转动方向(往后弯)
> 会让末端**先远离**目标,于是 CCD 一步都不肯迈,直接把小腿按在 0 度上 ——
> 整条腿退化成一根直杆绕髋摆动。加上"膝只许屈"的单侧窗口之后,真机表现就是
> **"拖脚踝往上,脚完全不动"**。实测:扫 10 个拖动方向,只有 1 个能到位;
> 向前上方抬 0.30 m 时误差 **0.213 m**(等于没跟手)。

解析式解的要点:

1. 父骨长 `L1 = |子关节.offset|`、末段长 `L2 = |效应器.offset|`(这个模型里两者都精确等于骨长);
2. 余弦定理给出"父骨与髋→目标"的夹角 α,以及膝角;
3. 膝的位置 = 髋 + L1 × (沿"髋→目标"偏 α 角、且**朝极点那一侧**的方向);
4. 转父关节把子关节原点送到膝上,转子关节把效应器送到目标上 —— 走的是同一套
   "转轴 + `eulerFromMatrix` + `clampJoint`",所以**限位照旧是唯一收口点**,这里绕不过去;
5. 迭代 8 轮只为收掉欧拉分解与限位夹取的残差。

**极点不写死"膝朝前"**,而是量出来的:把 hinge 关节按它窗口里行程更大的一侧转 15 度,
看末端往哪挪,取**反方向**就是膝(或肘)该鼓出去的那一侧(屈膝时踝往后走 ⇒ 膝往前鼓;
屈肘时腕往前走 ⇒ 肘往后鼓)。换模型、换命名都不会错。

效果:向前上方抬 0.30 m 的误差从 **0.213 m 降到 0.0003 m**,而且解出来的正是解剖学解
(髋前屈 +80、膝屈 -88)。剩下的误差全部出现在**目标超出腿长 0.774 m** 的时候 —— 那是物理不可达,
腿伸直去够、绝不反关节。

换回欧拉角的关键推导(CCD 与解析式解都要用到):关节在 bbox 空间里的朝向 = 父朝向 × 局部旋转矩阵,
记作 `P·L`。要把"在 bbox 空间里叠加一个旋转 Δ"写进去,就是 `P·L' = Δ·P·L`,于是

```
L' = P⁻¹ · Δ · P · L
```

再把 `L'` 用 `rig.eulerFromMatrix` 解回 `(x, y, z)`。旋转矩阵正交,`P⁻¹` 直接取转置。

**还欠着的一段**:胳膊的链是三节(肩 + 上臂 + 前臂),其中肩与上臂同原点,实际只有
上臂 + 前臂两段有效长度 —— 所以"拖手"理论上也能用闭式解,只是要把肩当作纯朝向关节先定平面。
现在走 CCD,实测多数目标 1~3 mm,个别方向 5 cm。不必急着做。

### 5.4 交互:按"抓到的是杆还是球"分两种操作(已落地)

小人的画法本身就把两种操作分开了:骨骼是锥形圆柱(**连接杆**),关节原点上有一颗球(**节点**)。
手指抓到什么,就做什么:

- **拖连接杆 = 绕该关节旋转**。力臂取**骨骼自身**(关节原点到末端),
  屏幕上解出让"末端走向与手指一致"的角度,所以不需要任何硬编码的正负号。
  力臂**不用"手指按住的那个点"**:细骨杆上能被判中的点离关节往往只有二三十像素,
  而手指一拖就是上百像素 —— 半径比手指行程还小,几何上根本到不了,线性解算只能给出
  一个夸张的角度(本机实测:拖 110 像素转出 146 度,末端绕一大圈跑到上面去),
  手感就是"甩飞"。用整根骨骼当力臂,半径等于骨长,正常拖拽都落在可达范围内。
  短骨骼(肩 10cm、脖子 7cm)按 `LEVER_MIN`(0.20m)兜底,顺带让各关节手感一致。
- 三个欧拉通道里,**屏幕上没反应的要先扔掉**:每弧度在屏幕上走不满最强通道
  `RESPONSE_SHARE`(0.55)倍的通道不参与解算。正对镜头时手臂的屈伸通道只有约 13 像素/弧度,
  那点位移完全来自透视;留着它硬解,竖直往下拖会解出"往前甩一大圈"。
  扔掉之后,竖直拖几乎不动、水平拖正常侧摆;把镜头转到侧面,屈伸通道自己变强。
  剩下的通道里取行列式最大的一对(屏幕上分得最开的一对),两轴几乎重合时退回单通道投影。
- **拖节点 = IK 移动**。目标点取"手指在过该节点、与镜头平行的平面上的落点",
  把屏幕位移原样加到节点原点上,再交给 CCD。走不到就是走不到(骨长是硬的)。
- **命中优先节点**:先按屏幕距离找 22px 以内的节点球,没找到才判连接杆;
  射线打空还有一层**胖射线**兜底(相机射线到骨杆线段的最短距离 < 骨骼半径 × 1.5)。
  手机上骨杆只有几十像素宽,细射线经常擦过去。
- **选中关节后拖三条滑杆**(底部 sheet 里):精确微调,也能表达 IK 解不出来的角度(比如自转)。
- 相机用已经内置的 OrbitControls,单指转、双指缩放平移。
- 撤销重做用姿态快照栈:姿态本来就是纯角度数据,快照极便宜,不需要命令模式。

`rig.ikChain` 决定拖一个节点时"往上转哪几节":肢体只走肢体链(碰躯干就停),
躯干沿脊柱往上走,**hips 与 broot 永不进链** —— 骨盆一动,全身连脚都跟着走,
那是"搬运"该干的事。链为空(例如肩球)时只能旋转 —— 抓到球之后走移动还是旋转,由 `rig.grabMode` 一处判定,
视口的三个命中入口(节点屏幕距离、射线、胖射线)都问它,免得各说各话。

## 7. 设备上的前置验证(阻塞项)

**设备 WebView 的 WebGL 可用性没验证过**,而它是整条 3D 路线的唯一前置风险。

版本层面已经查清,没有问题:

- Android WebView 自 **Android 5.0**(Chromium M37)起就支持 WebGL,并可通过应用商店更新。
- **WebView 58 起完整支持 WebGL 2**。我们的目标设备是 Chrome 83 量级,远高于这条线。
- 内置的 three.js r147 会按 `webgl2 → webgl → experimental-webgl` 顺序取上下文,拿不到 WebGL2 会自动退回 WebGL 1,两层都支持。

真正的风险是**设备级而不是版本级**:WebView 不允许覆盖 Chromium 的 GPU 黑名单。
如果该机型的 GPU 驱动被判定为黑名单(历史上有 Mali-T604 这类先例),
WebView 里的 WebGL 会被静默禁用——此时同一台机器上的 Chrome 可能还能正常显示。
所以结论是:可以基于 three.js 做,但必须先在目标设备上实测一次 WebGL 上下文,
不能凭版本号放行。页面里已经内置了这项自检(`app/features/self-test.js` 的 `webgl` 项),
连上设备读一次页面状态就能判决。

另外两件要在实现时一并处理的 WebView 特性:

- **上下文丢失**:长时间后台或显存紧张时 WebView 会丢 WebGL 上下文,
  必须监听 `webglcontextlost` / `webglcontextrestored` 并重建资源,否则回前台就是黑屏。
- 若 WebGL 最终不可用,只能退回 Canvas 2D 的骨架编辑器(画关节与骨链,没有立体感),
  产品形态会明显不同。

## 9. 面向后续扩展的结构预留(双脚固定、物理倒下、更多骨骼控制)

先说结论性判断:**"双脚固定"和"物理倒下"不是两件事**。

- 双脚固定 = 末端约束(锁位置与朝向)+ 多链同时求解 + 可选的平衡约束。这是运动学问题。
- 物理倒下 = 把同一批关节约束交给动力学求解器去满足,再叠加碰撞与重力。

所以现在要定的不是"要不要上物理",而是把下面四处结构留成可替换的。
这四处现在做几乎零成本,以后再补就是重写:

1. **姿态是唯一真相**(已经成立)。物理引擎的输出必须写回同一个姿态结构,
   渲染、存储、导出、姿态库只认它,不认谁是产生者。
2. **关节约束表是数据,并且预留字段**。今天只用它做范围夹取;
   以后同一张表直接翻译成物理引擎的关节约束(球窝/铰链 + 范围 + 刚度/阻尼/驱动模式)。
   这一条是全部扩展里最关键的决定:约束写在代码里就锁死了,写在表里就什么都能接。
3. **求解器是一层可替换的东西,接口统一**:`solve(constraints[], pose, dt) → pose`。
   - 现在:解析两骨 IK + 自写 CCD + 范围夹取。
   - 以后:同一个接口换成"物理步进 + 目标驱动"。
   - 双脚固定只是约束列表里多两条 `{ effector: foot.L / foot.R, mode: fixed }`,不是新架构
     (第 10 节把这条泛化成了通用约束)。
4. **UI 与数据层从第一天承认姿态有不同来源**:编辑模式(运动学,精确可复现)与
   物理模式(动力学,自然但同样初始条件每次结果不同)。模式是数据字段,不只是界面开关。

### 物理引擎候选(许可已核实)

| 引擎 | 许可 | 形态 | 对这台设备 |
|---|---|---|---|
| `schteppe/cannon.js` | MIT 5002★ | 经典脚本 UMD,数百 KB | 最省事,已停更但稳定 |
| `lo-th/Oimo.js` | MIT 3175★ | 经典脚本 UMD,约 100KB | 最小,适合旧 WebView |
| `pmndrs/cannon-es` | MIT 2060★ | ESM / CJS,无 UMD | 与零构建约束冲突 |
| `dimforge/rapier` | Apache-2.0 5766★ | WASM,异步初始化 | 性能好,旧设备首帧编译与内存有风险 |
| `kripken/ammo.js` | 许可未自动标注 | Bullet 移植,WASM/asm.js,>1.5MB | 体积与内存不划算 |
| 自写 verlet + 关节约束 | 无依赖 | 约 300 行 | 可控,但 ragdoll 稳定性与自碰撞要自己啃 |

真要上物理时,优先 Oimo.js 或 cannon.js(经典脚本、体积可控)。
"自己倒下"还必须有自碰撞与地面接触,否则效果只是穿模加倒地不起。
WASM 方案在这台设备上不作为首选。

### 现在不做的理由

1. 设备 WebGL 还没验证,物理要建在 WebGL 之上。
2. 双脚固定本身是运动学问题,先做它就能验证第 3 条那个接口设计得对不对。
3. 物理摆姿会牺牲"精确复现",它只能是**一种模式**,不能是唯一真相。

- ~~锁定空间默认值~~:已定 `space: "bbox"`(第 10 节),即默认锁在人物子空间里。
- 冲突优先级策略:两条锚在 `world` 的约束打起来时,是拒绝后写入的一条,还是踢掉优先级低的一条?
- 硬锁还是软锁默认:`stiffness: 1`(拖不出范围)还是默认带一点柔性(能拖出去、松手回弹)?
  后者手感更"物理",但要求求解器从第一天就支持刚度,而不是只做夹取。
- 要不要"自动恢复站立":那需要重心与平衡约束,复杂度上一个台阶。

- 包体与性能底线:允许加约 100KB 级别的 JS 物理引擎,还是完全不加依赖(那就要自写)?

## 10. 把"锁定"泛化成通用约束(采纳)

原始想法是"双脚固定"。把它泛化成"可以锁定任意一个或多个节点"是对的,而且更强:
手、脚、头、肘都能锁,锁脚只是"往约束表里加两条"的一种预设。

采纳之后,这一层就从"一个功能"变成整个应用的核心结构:**约束表**。
拖拽与锁定也随之统一——拖拽是瞬时约束,锁定是持续约束,两者走同一条求解路径。

### 先看清一件事:"锁定"的本质是**选一个参考系**

同一句"锁定这个关节",底下可能是两件相反的事。差别不在锁什么,而在**锁在哪个参考系**:

| | **锚定 anchor** | **冻结 freeze** |
|---|---|---|
| 锁在哪个参考系 | 比它高的某一层(bbox / 祖先关节 / world) | 它自己的直接父关节 |
| 含义 | 这个点在那个参考系里不许动 | 这个关节的局部角度不许变 |
| 参考系移动时 | 目标不动,由上游 IK 去适配 | 跟着参考系一起动 |
| 谁来满足 | IK 求解器(需要反解上游链条) | 求解前的过滤条件,零成本 |
| 典型用法 | 脚踩地面、手扶桌面、头保持朝向 | 暂时封住某个关节,避免手滑改到 |

只做一个"锁定"开关,一定会做出一个"锁了但看起来没生效"的功能。
所以约束项的第一要素不是"锁位置还是锁旋转",而是 `space`——**钉在哪一层**。

### 三层参考系:bbox → broot → hips,以及"锁定"钉在哪一层

锁定的参考系不是骨盆,而是**人物所在的子空间**——一个可以整体搬走的立方体容器 bbox。
下面这个模型取代了此前"只有 world / parent 两个空间"的写法(那版把关键的一层漏掉了)。

**先说最根本的一条原理,它决定了整个设计:**

> **锁定钉在哪一层,取决于你打算动哪一层。锚在你要动的东西之上 → 需要 IK;
> 锚和你要动的东西一起动 → 零成本,连锁定一起被搬走。**

这条原理把"锁住一只脚"干净地分成两个互不干扰的操作:

| 你要做的动作 | 锁定钉在哪一层 | 代价 |
|---|---|---|
| 摆骨盆、掰腿调姿势 | 锚在 bbox(容器) | 跑 IK:腿自动反解,让脚在 bbox 里不动 |
| 把人整体搬到场景另一边 | 搬 bbox 本身 | **零成本**:脚在 bbox 里没动过,跟着一起走 |
| 让脚踩住地面、身体挪开 | 锚在 world(地面) | 跑 IK,且可能把人拉得站不住 |

**三层参考系(从外到内):**

```
world      场景与地面。相机、参考线、地面都在这一层。
 └ bbox    人物所在的子空间 = 一个可平移 + 可旋转的立方体容器。
           搬动它 = 连人带脚一起走,零成本。
           每个角色实例一个(将来多角色就是多个 bbox)。
    └ broot 骨架顶层节点。相对 bbox 的变换。
           动它 = 人在原地挪位 / 转身,锁定的脚留在 bbox 里 → 跑 IK。
       └ hips(骨盆)  ← 原有 18 个关节全挂在这条链下面
          ├ spine → chest → neck → head
          ├ shoulder.L/R → upperArm → foreArm → hand
          └ thigh.L/R → shin → foot
```

**为什么 bbox 与 broot 不能合成一个:因为"搬运"和"转身"必须是两件事。**
合成一个之后,转动整个人必然带着脚一起转(脚在参考系里没动,零成本),
就再也做不出"脚不动、上半身转过去"这个动作了。行业里也是两层:UE 的 Actor 有
Root Component(≈ bbox),其下 SkeletalMesh 里还有 root bone(≈ broot);
搬 Actor 是搬容器,动 root bone 是骨架级操作。

**骨架顶层叫什么。** 行业统一叫 `root`,各管线只是大小写差异:

| 管线 | 骨架顶层 | 它的直接子级 | 骨架之外的容器 |
|---|---|---|---|
| UE5 | `root`(必须在世界原点) | `pelvis` | Actor Root Component |
| VRM | `Root` | `Hips` | 场景节点 |
| Blender / Unity 通用骨架 | `root` | `pelvis` / `Hips` | 父级 Empty / GameObject |
| HumanIK | 不映射 Root,直接从 `Hips` 起算 | - | - |

本项目把这两层定名为成对的一组:**`broot`(body root,骨架顶层)与
`bbox`(body box,人物子空间)**。名字成对、一眼看得出谁套着谁,
也不会和 three.js 的 `scene` / `Object3D` 这类通用叫法混淆。

**已落地并在真机验证(2026-09-24)**:`app/core/rig.js` 表里的第一项就是 `broot`
(`parent: ""`、`offset: [0,0,0]`、`radius: 0` 的纯变换节点,标记 `pivot: true`),
`hips.parent` 已改为 `"broot"`,关节数 19 → 20;
`app/components/viewport.js` 的场景图是 `scene → bbox(Group) → broot → hips → …`,
搬运模式直接平移 `bbox.position`,姿态一个字节都不改。

**一处必须纠正(上一版说错了):"位置锁定只在世界空间才有意义"是错的。**
正确的说法是:

- 刚性骨架里,关节相对**直接父关节**的位置本来就是常量(`offset` 恒定),
  所以 `space` 取"直接父关节"时 `position: "locked"` 是恒真的空操作,写入时就该报错;
- 但在**任何比它更高的参考系**(bbox / 任意祖先关节 / world)下,位置锁定都有真实语义,
  因为那些参考系可以独立于它移动,代价是要跑 IK 反解上游链条。

也就是说 `space` 不是"世界 / 父级"二选一,而是**一条参考系链**:

```
space: "bbox"(默认) | "world" | 任意祖先关节名 | "broot"/"hips"/... | "parent"
```

- **默认 `"bbox"`**:锁脚就是锁在人物子空间里——摆骨盆要跑 IK,搬 bbox 零成本。
  这才是使用者说"锁住这只脚"时想要的默认行为。
- **`"world"`**:踩在地面上,搬 bbox 时脚留在原地。必须显式选,因为它会和 bbox 对抗。
- **任意祖先关节名**(如 `"chest"`):"手相对胸口固定"这类约束,钉在链上的任意一层。
- **`"parent"`**:纯 FK 冻结,只用来封住该关节自己的旋转自由度,不做 IK。

### 约束项的形状

```
{
  joint:    "foot.L",                    // 任意关节,含 "broot"
  space:    "bbox",                      // 钉在哪一层参考系,默认 "bbox"
  position: "free" | "locked",           // 取直接父关节时非法(恒真的空操作)
  rotation: "free" | "locked",           // 任何参考系下都有效
  priority: 0,                           // 冲突时的取舍顺序
  stiffness: 1                           // 1 = 硬锁;小于 1 表示允许带偏差(手感更软)
}
```

目标值的存储约定:**存"在 `space` 这一层里的坐标与朝向",不存世界坐标。**
这是让"搬 bbox 零成本"成立的唯一办法——bbox 一动,参考系跟着变,目标值无需重算。

`stiffness` 就是第 9 节说的那个预留字段,在这里第一次派上用场。

### 求解流程

0. 应用 `bbox` 与 `broot` 的变换。**只要约束表里没有 `space: "world"` 的项,
   这一步不触发任何重解**:锚在 bbox / 祖先 / parent 上的约束都是相对参考系定义的,
   参考系变换了,它们的目标相对同一个参考系也没变。
   只有锚在 `world` 的约束,才会因为 bbox 或 broot 动了而需要重解。
1. 收集约束表。取出 `space: "parent"` 的:锁旋转 → 把该关节的角度通道标记为只读
   (求解器不许改);出现锁位置 → 非法组合,直接报错。
2. 其余约束按 `priority` 从高到低排序;锚在 `world` 的排前面,它最容易无解。
3. 逐条求解:把目标点从它的参考系变换到 bbox 局部,以该关节为 effector,
   对上游链做 IK(手脚下肢走解析解,脊柱与多链走 CCD)。
4. 每轮求解后统一过一遍解剖范围夹取(第 5.2 节),这是唯一的写入口。
5. 记录每条约束的残差。**解不出来时必须可见**(提示"这条约束达不到"),
   而不是静默地留在错误位置上——静默错位是这类工具最难查的 bug。

消歧原则:链上还有剩余自由度时(两骨链锁住末端点后还剩 1 个自由度),
按"从当前姿态出发旋转最小"来定解,而不是随机解。这样拖拽不会让姿态突然跳变。

### 这个泛化带来的好处

- 锁双脚、锁单脚、锁手扶墙、锁头朝向,全都是一行数据,不需要各自的功能开关。
- 与拖拽统一:拖拽就是"临时锚到鼠标位置"的一条约束,解除拖拽即移除。求解器只需一种输入。
- **整体搬运零成本**:锚在 bbox 上的约束,在搬动 bbox 时一次 IK 都不用跑。
  这是把参考系做成"可搬运的容器"而不是"世界坐标"换来的,也是这个设计最实用的一点。
- 与物理对接干净:`position: locked` 对应物理里的固定约束,`rotation: locked` 对应锁转轴;
  同一个约束表可以喂给运动学求解器或物理引擎,这正是第 9 节想要的"约束表当数据"。
- 体操、托举、扶桌、坐姿这类姿势本质都是"多点锁定",做完这一层它们就都成立了。

### 风险与边界

- **过约束无解**:同时锁双脚 + 锁双手,人物被完全定住,此时再拖身体就可能不可达。
  必须有优先级与残差反馈,不能假装成功。
- **越锁越难**:两骨链锁住末端后剩 1 个自由度,再锁旋转就要求精确解;锁得越多,无解概率越高。
  界面上应该能看到"当前几条约束、哪条没满足"。
- **链范围**:锁头部位置时,要明确"允许被调整的是脖子以上还是整条上半身"。
  建议约束项支持一个可选的链范围,默认取合理值(头只调颈与上胸),避免拖头把整条脊柱拽歪。
- **锚在 `world` 的约束会和 bbox 对抗**:搬动 bbox 时脚留在原地,人越拉越远,
  最后残差不为零。这类约束在界面上要有醒目标记(比如锁图标带一个"地面"角标),
  让使用者知道"我搬的盒子跟这个锁定在打架",而不是看到一个静默的错位。
