# 3D 摆姿场景的技术选型

日期:2026-09-24。范围:只讨论 3D 摆姿场景本身,不含模型生图。

## 1. 目标与硬约束

要做的事:一个简化人体模型(宜家小人那种)、骨架绑好、可拖拽关节移动与旋转、摆出各种姿势、
正反向运动学、并限制在正常人体可能的骨骼旋转范围内。

硬约束来自 Hermit happ 本身(见 `AGENTS.md`):

- 纯原生 HTML / CSS / JavaScript,没有构建步骤,不使用打包器。
- 不联网加载模块,不引 CDN。第三方库必须原样放入 `vendor/`。
- 兼容 Android 10 与旧厂商 WebView,实测等价 Chrome 83。
- MIT 许可,因此不能混入 GPL 代码。

## 2. 先澄清一个术语

这里说的"正反向动力学",在摆姿场景里实际指的是**运动学 kinematic**:

- **FK 正运动学**:给关节角度,算出手脚末端在哪。我们只做"把角度写进层级"就完事了。
- **IK 反运动学**:给手脚末端目标位置,反解出关节角度。这是"拖手拖脚"手感的来源。
- **动力学 dynamics**:力、质量、惯性、重力、碰撞。MagicPoser 宣传的"物理引擎自动生成自然姿势"
  属于这一层。

结论:摆姿这个场景 95% 的体验价值在 FK + IK + 关节限制。动力学是加分项,第一版不做,
最多后面加一个"重心投影提示"这种很轻的辅助。把动力学当成必做项会把工作量放大一个量级,
而收益主要在极端姿势与摔倒动作,不是我们要的东西。

## 3. 开源项目调研(许可已逐个核实)

| 项目 | 许可 | 算法 | 关节限制 | 对我们可用性 |
|---|---|---|---|---|
| three.js 自带 `CCDIKSolver` | MIT | CCD | r147 经典脚本版只有单轴 `limitation`;r160 起重写为 `rotationMin/rotationMax` 欧拉盒夹取 | 需要 `mesh.skeleton.bones`,即要求 SkinnedMesh |
| `lo-th/Fullik` | MIT(471★) | FABRIK + CCD | 支持逐关节约束 | 有经典脚本,但 API 重、按老版 three 写 |
| `jsantell/THREE.IK` | MIT(586★) | FABRIK | 提供 `constrain()` 钩子,范围自己写 | 需要自己转成经典脚本 |
| `upf-gti/IK-threejs` | MIT(23★) | CCD + FABRIK | 有 ball-socket / hinge 与角度范围,最贴需求 | 只有 ESM 源码,零构建步骤下不能直接用 |
| `boytchev/mannequin.js` | **GPL-3.0**(430★) | 只有 FK,没有 IK | 没有硬性角度限制,只提示"负值不自然" | **代码不能进 MIT 项目** |
| `Callum-OP/3D-Character-Animator` | 无许可声明 | 变换 gizmo,非 IK | 无 | 只能看思路,不能复用 |

三个关键事实是我读源码确认的,不是猜的:

1. three.js r147 的 `examples/js/animation/CCDIKSolver.js` 确实存在,导出 `THREE.CCDIKSolver`
   与 `THREE.CCDIKHelper`,是经典脚本,能用。但它内部直接 `this.mesh.skeleton.bones`,
   **必须要一个 SkinnedMesh**,我们这种刚性分体小人用不了(除非造假对象绕开,见 5.3)。
2. 同一份 r147 文件里**没有** `rotationMin` / `rotationMax`,只有单轴 `limitation`。
3. r160 才加了 `rotationMin` / `rotationMax`,实现方式是:每一轮 CCD 迭代之后,
   把该 link 的欧拉角按分量夹进给定范围。

第 3 条很重要,它说明连 three.js 官方对"关节限制"的处理方式就是**迭代后夹取**,
不是把约束做进求解过程。这给了我们自己写求解器的正当性。

## 4. MagicPoser 与 SetPose 的技术对照

MagicPoser(`webapp.magicposer.com`)对外说明的能力:符合人体解剖与运动学的求解器、
手部与脚部的成熟 IK、拖拽控制点摆姿、物理引擎自动生成自然姿势、逐指控制、姿态库与镜像。

它的交互范式是"每个关节一个控制点,拖就是了"。这对我们没有直接可抄的代码(GPL 与闭源),
但指出了三件事必须做到:IK + 解剖限制 + 语义化的关节控制。

更值得抄的是 **SetPose**(同样 three.js 系,构建在 mannequin.js 之上)的做法,它更接近"简单够用":

- 每个肢体只有三个语义通道:**Bend(屈伸)/ Tilt(侧摆)/ Rotate(自转)**,不是自由欧拉角。
- 一个 **Biological constraints 开关**:打开按关节活动范围限制,关闭则放开到 ±180,允许夸张造型。
- 道具可以 attach 到关节上,换姿势时跟着走。

第四个参考是 mannequin.js 自己的关节命名:手臂与腿用 `raise / straddle / turn`,
头用 `nod / turn / tilt`,躯干用 `bend / turn / tilt`。这说明"按解剖语义命名三个通道"
不是权宜之计,而是一个成熟库的选择。

## 5. 建议方案

### 5.1 模型:自己程序化生成的刚性分体小人

每根骨头 = 一个 `THREE.Bone`(或 Group) + 一个挂在它下面的胶囊/圆柱/球 mesh,父子层级就是骨架。

- 不需要蒙皮、不需要骨骼权重、不需要 GLTFLoader。
- "宜家小人"本就是分体结构,弯曲处本来就不需要平滑过渡,所以这不是妥协,而是正解。
- 零素材许可风险(全部由代码生成)、零加载器、包体极小、关节位置清晰可见。
- 后面若要换成真角色:CC0 蒙皮 GLB 有 Quaternius、Kenney、KayKit、100 Avatars 可选。
  代价是加 GLTFLoader 与 SkeletonUtils,并且与 IK 方案冲突(见 5.3)。
  Mixamo 免费但不可再分发,不适合随包发布。

### 5.2 关节模型:语义化三通道 + 解剖范围表

这是整个方案的地基。每个关节声明三件事:类型(球窝 / 铰链 / 固定)、三个通道名、每个通道的范围。

```
肩  shoulder   球窝  raise -90..180   straddle -45..135   turn  -90..90
肘  elbow      铰链  bend    0..150                       (负值即反折,禁止)
膝  knee       铰链  bend    0..150                       (方向与肘相反)
髋  hip        球窝  raise -30..120   straddle -25..45    turn  -45..45
踝  ankle      铰链  bend  -20..45    tilt     -20..20
腰  spine      球窝  bend  -30..45    tilt     -25..25    turn  -45..45
胸  chest      球窝  bend  -20..30    tilt     -20..20    turn  -40..40
颈  neck       球窝  nod   -40..30    tilt     -30..30    turn  -60..60
```

内部存四元数或欧拉都行,但**编辑入口只有这三个语义通道**,写进去之后立刻过一遍范围夹取。
这样有两个好处:

- 手感好:屈伸和侧摆不会互相污染,拖一个通道就是那个通道。
- 结构上不可能出现反关节:任何写入路径(滑杆、IK、预设、镜像、姿态导入)都过同一个夹取点。

`app/core/rig.js` 现在是纯欧拉角 `{x,y,z}`,建议改成"语义通道 + 映射函数",
并且**镜像要跟着一起改**——镜像的对象是通道名与通道值的左右对应关系,而不是直接对欧拉角取反。

### 5.3 IK:解析式两骨 + 自写 CCD,约 200 行,不引依赖

分两层,这是"优秀"的关键:

1. **解析式两骨 IK**(约 80 行):给定手腕或脚踝的目标点,直接解出上臂+前臂(或大腿+小腿)
   两组角度,再按"肘窝朝向"约束极向。闭式解,没有迭代、没有抖动,可以精确保证肘膝不反折。
   覆盖"拖手、拖脚"这两个最高频操作。
2. **自写 CCD**(约 120 行):给脊柱链、多骨链、以及"拖头、拖腰"这种没有闭式解的情况兜底。
   每轮迭代后对每个关节做 5.2 的范围夹取(与 three.js 官方同一思路)。

为什么不直接引库:

- `IK-threejs` 只有 ESM 源码,零构建步骤下不能直接用;手工转换等于改第三方代码,违反
  `AGENTS.md` 里"vendor 必须是原样发行文件"的约定。
- `THREE.IK` 与 `Fullik` 也需要打包或版本适配。
- three.js 自带的 CCD 求解器要 SkinnedMesh。绕开的办法是鸭子类型:
  它只读 `mesh.skeleton.bones`,所以可以塞 `{ skeleton: new THREE.Skeleton(bones) }` 进去。
  这是可行的,但 r147 那份没有角度范围,仍要自己加夹取,省下的只是 CCD 迭代本身,
  而 CCD 迭代恰好是最好写的那部分。所以直接自己写更划算。

### 5.4 交互:两级精度

- **直接拖关节球**(手、脚、头、腰,可选肘膝的极向调整):走 IK,快速定大形。
  实现是 pointer 事件 + 射线投到"过当前关节、正对相机"的平面,得到目标点。
- **选中关节后拖三个通道**(滑杆或圆环):精确微调,同时也能表达 IK 解不出来的角度。
- 相机用已经内置的 OrbitControls,单指转、双指缩放平移。
- 撤销重做用姿态快照栈:姿态本来就是纯角度数据,快照极便宜,不需要命令模式。

### 5.5 与现有骨架的关系

`app/core/rig.js` 已有的东西继续用:关节层级、默认站姿、镜像、前向运动学、序列化。

要补的是两块:

1. 5.2 的关节类型与三通道范围表,作为夹取的唯一出处。
2. 语义通道与存储表示的换算(含镜像)。

`app/components/viewport.js` 从空实现变成:建 mesh 与灯光、相机、拾取、拖拽、渲染循环、
截图。`app/features/poser.js` 从"只改角度"变成拖拽与 IK 的编排。

## 6. 落地顺序(每一步都能单独验收)

1. 视口:小人 + 轨道相机 + 地面网格,先让画面立起来。
2. 拾取与选中:点关节高亮,三通道滑杆驱动纯 FK。
3. 解剖范围夹取 + 反关节回归测试(写进 `tests/`)。
4. 解析式两骨 IK:拖手、拖脚。
5. 自写 CCD 兜底:拖头、拖腰。
6. 姿态库落盘与撤销重做。

## 7. 设备上的前置验证(阻塞项)

**设备 WebView 的 WebGL 可用性没验证过**,而它是整条 3D 路线的唯一前置风险。
目标 WebView 是 Chrome 83 量级,理论上 WebGL 1.0 从 Chrome 8 就有,应该没问题,
但旧厂商 WebView 关掉硬件加速是有先例的。页面里已经内置了这项自检
(`app/features/self-test.js` 的 `webgl` 项),连上设备读一次页面状态就能判决。

若不可用,只能退回 Canvas 2D 的骨架编辑器(画关节与骨链,没有立体感),
产品形态会明显不同,所以这一项应该优先确认。

## 8. 明确不做的事

- 不做蒙皮、骨骼权重、glTF 角色导入(除非以后要导出真角色)。
- 不做物理引擎、重力、碰撞、布料。
- 不做逐指控制,手就是一个整块(够用;MagicPoser 的逐指是付费卖点,但我们的目标是摆姿势轮廓)。
- 不引入任何 IK 依赖库。
